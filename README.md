# tls-demo

**TLS 1.3 のハンドシェイクから HTTPS までを、ブラウザ内のモックサーバーで最初から最後まで再現する教材デモ。**

「https の鍵マークが付いているとき、裏で何が起きているのか」を 1 画面で追えるようにしたもの。
**証明書チェーン / ホスト名照合 / 有効期限・失効 / CertificateVerify / Finished / 前方秘匿性 / レコード暗号化** の各防御をトグルで OFF にすると、対応する攻撃が成立する様子を体験できる。

鍵生成・鍵導出・署名・暗号化はすべてブラウザの Web Crypto 上で動作し、実在のサーバーには接続しない。鍵はタブの外に出ない。

## TLS を 5 つの層で捉える

```
TLS
├── Handshake        # 接続時に何をしているか
├── Certificate      # サーバーが本物か確認
├── Key Exchange     # 共通鍵を安全に共有
├── Encryption       # 以降の通信を暗号化
└── HTTPS            # HTTP を TLS で保護したもの
```

HTTPS は実際にこの順で動く。**TLS ハンドシェイク → 証明書の検証 → 鍵交換 → 共通鍵で暗号化 → その上で HTTP 通信**。
このデモの画面構成も、防御トグルもこの 5 層に沿って並べてある。

なお、この 5 つは「順番に実行される 5 工程」というより、**1 回のハンドシェイクの中で同時に絡み合う 5 つの関心事**に近い。
たとえば鍵交換の材料（key_share）は最初の ClientHello に既に乗っているし、証明書の検証はその鍵で暗号化された中で行われる。

## フローの考え方

### 「鍵を作る」と「相手を確かめる」は別の仕事

TLS の核心は、この 2 つが**独立した別々の問題**だという点にある。

- **鍵交換（Key Exchange）** は、盗聴者に見られている経路で共通鍵を作る技術。ECDHE がこれを解く。
- **証明書（Certificate）** は、その鍵を共有した相手が誰なのかを確かめる仕組み。CA の署名がこれを担う。

**鍵交換は中間者とも問題なく成功してしまう。** ECDHE は「誰かと安全な通信路ができた」ことしか保証せず、その誰かが銀行なのか攻撃者なのかは何も言わない。
だから証明書の検証を省くと、暗号化はきちんと効いているのに中身は攻撃者に筒抜け、という状態が成立する。逆に証明書だけ完璧でも、鍵交換が弱ければ通信は守れない。両方が要る。

### ハンドシェイクの全体像

`═══` は**平文**の区間、`───` は**暗号化済み**の区間。番号は画面の手番と対応している（正常フローは 12 手）。

```
  クライアント (ブラウザ)                                サーバー
       │                                                  │
       │  ① ClientHello                                   │
       │     対応バージョン / 暗号スイート一覧 / SNI       │
       │     + key_share（使い捨て公開鍵 A）               │
       │═════════════════════════════════════════════════▶│
       │                                                  │
       │  ② ServerHello                                   │
       │     選んだ暗号スイート + key_share（公開鍵 B）    │
       │◀═════════════════════════════════════════════════│
       │        ここまで平文。この 2 通だけで鍵が決まる     │
       │                                                  │
       ├─── ③ ECDHE: aB = bA = abG（共有秘密）────────────┤
       ├─── ④ HKDF: Early → Handshake → traffic 鍵 ───────┤
       │                                                  │
       │  ⑤ Certificate（証明書チェーン）                  │
       │  ⑦ CertificateVerify（秘密鍵の所持証明）          │
       │  ⑧ Finished（ここまで全文の MAC）                 │
       │◀─────────────────────────────────────────────────│
       │        handshake 鍵で暗号化済み                   │
       │                                                  │
       ├─── ⑥ 証明書の検証（チェーン / SAN / 期限）───────┤
       │                                                  │
       │  ⑨ Finished                                      │
       │─────────────────────────────────────────────────▶│
       │                                                  │
       ├─── ⑩ HKDF: Master → application 鍵へ切り替え ────┤
       │                                                  │
       │  ⑪ POST /api/transfer（ただの HTTP）              │
       │─────────────────────────────────────────────────▶│
       │  ⑫ 200 OK                                        │
       │◀─────────────────────────────────────────────────│
       │        application 鍵で暗号化済み                 │
```

読みどころは 3 つ。

1. **平文なのは最初の 2 通だけ。** TLS 1.3 は ClientHello に鍵交換の材料を相乗りさせることで、往復 1 回で鍵を決めてしまう。証明書すら暗号化された後に流れる（TLS 1.2 では平文だった）。
2. **平文区間に秘密は流れない。** 経路に出るのは公開鍵 A と B だけで、そこから共有秘密 abG を求めるのは離散対数問題そのもの。ただし **SNI（接続先ホスト名）は平文のまま**で、TLS でも隠れない。
3. **HTTPS の層は驚くほど薄い。** ⑪⑫ でやっているのは、普通の HTTP のバイト列をレコード層に流し込むことだけ。HTTPS という別のプロトコルがあるわけではない。

### transcript hash がすべてを縛っている

TLS 1.3 の改ざん耐性は、ほぼこの一点に集約される。

**ここまでに交換した全メッセージのハッシュ（transcript hash）が、鍵導出と Finished の両方に入力されている。**

```
Derive-Secret(Secret, "c hs traffic", Transcript-Hash(ClientHello..ServerHello))
verify_data = HMAC(finished_key, Transcript-Hash(ClientHello..CertificateVerify))
```

経路上でメッセージを 1 バイトでも書き換えると、クライアントとサーバーの transcript が食い違う。すると:

- 導出される鍵が別物になり、以降のレコードを**復号できない**
- Finished の verify_data が**一致しない**

改ざんを「検出する」というより、**改ざんすると通信そのものが成立しなくなる**。ダウングレード攻撃が TLS 1.3 で通らないのはこのため。

### 証明書は何を証明していて、何を証明していないか

証明書まわりの防御が 4 つに分かれているのは、それぞれ**別のことを確かめている**から。1 つでも欠けると、そこだけを突く攻撃が成立する。

| 防御 | 確かめていること | これがないと |
| --- | --- | --- |
| チェーン検証 | 信頼ストアのルート CA まで署名を辿れるか | 誰でも自分で CA を立てて証明書を発行できる |
| ホスト名照合 | その証明書は**この接続先のもの**か | 攻撃者が自分の正規証明書で他人に成りすませる |
| 有効期限・失効 | 今も有効か、取り消されていないか | 漏洩した鍵を無効化する手段が機能しない |
| CertificateVerify | 相手が**秘密鍵を持っている**か | 証明書は公開情報なのでコピーすれば誰でも名乗れる |

特に最後の 1 つが見落とされやすい。**証明書そのものは秘密ではない。** 正規サーバーに繋げば誰でも取得できる。
だからサーバーは、ハンドシェイク全文に証明書の公開鍵と対になる秘密鍵で署名して見せる。この署名が検証できて初めて「証明書の持ち主本人」だと分かる。

### 前方秘匿性 — 「今は安全」と「ずっと安全」の違い

鍵交換に**接続ごとの使い捨て鍵**を使うのが ECDHE の E（ephemeral）。長期鍵は署名にしか使わない。

これが効くのは「攻撃者が今日の暗号文を全部記録しておき、後日サーバーの秘密鍵を手に入れる」というシナリオ。

- **長期鍵で鍵交換していた場合**: 記録しておいた通信を、鍵スケジュールごと再現して**すべて遡って復号できる**。
- **ECDHE の場合**: 鍵交換に使った秘密鍵は接続終了時に捨てられ、どこにも残っていない。長期鍵を手に入れても過去の通信は読めない。

このデモでは、実際に長期鍵から鍵スケジュールを再現して記録済みレコードの復号を試み、成否を表示する（`attemptRetrospectiveDecryption`）。

## 画面

1 画面を 4 つの区画に分けてある。上が状態、中央が観察、右が守り、下が攻撃。

```
┌─ 状態 ────────────────────────────────────────────┐
│ 接続確立 / 暗号スイート │ 盾 ●●●●●●● 7/7 │ 突破 0/8 │
├─ 盤面（観察）───────────────────┬─ 守り（操作）───┤
│ Handshake Key Exch. Cert. …     │ Finished 照合 ◉ │
│ [クライアント]══封筒══[サーバー]  │ チェーン検証   ◉ │
│ 👁 盗聴者に見えているもの         │ ホスト名照合   ◉ │
│ 経路 🔓CH 🔓SH 🔒Cert 🔒Req 🔒Res │ 有効期限・失効 ◉ │
│ 手持ち 🔑公開鍵 abG hs鍵 app鍵   │ CertificateVerify◉│
│ ▶再生 ◀▶↺  ①②③④⑤⑥⑦⑧⑨⑩⑪⑫    │ 前方秘匿性     ◉ │
│ ⑤ Certificate  OK               │ レコード暗号化 ◉ │
├─ 攻撃（操作 + 結果）─────────────┴─────────────────┤
│ [偽CA] [別ドメイン] [期限切れ] [失効] …  計 8 枠     │
│ 選んだ 1 つの詳細と、通った場合は盗まれた平文         │
└──────────────────────────────────────────────────┘
```

### 盤面 — 1 手ずつ再生する

全部の手を一度に並べると読む前に諦めてしまうので、**いま何が起きているか 1 手だけ**を出す。
▶ を押すと自動で進み、つまみを押せば好きな手に飛べる。正常フローは 12 手。

- **5 つの層の札**は進捗バーではない。順番に実行される工程ではないので、札の下に「その層が何手目を担当しているか」を出してある。Handshake が `1 2 8 9` と離れて出てくること、Key Exchange (`3 4`) が Certificate (`5 6 7`) より先に終わることが、そこで分かる。並びは最初に出てくる手が早い順。
- **封筒が経路を渡る。** 平文の手は破線＋開いた錠、暗号化済みの手は実線＋閉じた錠。手元の計算の手は封筒が飛ばず、歯車が回る。
- **盗聴者の窓が経路の真下にある。** 手を進めると、最初の 2 通は中身が読めていて、鍵ができた瞬間から読めなくなる、という切り替わりが同じ場所で目に入る。
- **経路の帯**に、通信全体（ClientHello / ServerHello / 証明書フライト / HTTP 往復）の封の有無を並べてある。「平文なのは最初の 2 通だけ」が一目で分かる。押すとその手に飛ぶ。
- **手持ちの帯**に、使い捨て公開鍵 → 共有秘密 abG → handshake 鍵 → application 鍵 が灰色から色付きに変わっていく。鍵が「いつ」生まれるのかを示す。
- 説明は見出し 1 行と本文 1 文だけ。専門用語の詳細と実際に計算された値（transcript hash、共有秘密、導出された鍵、証明書の中身、verify_data）は「くわしく」の中。

### 守り — 7 つのスイッチ

盤面の隣に置いてある。外すと手順そのものが変わり（該当する手が「省略」になる、あるいは接続が中止される）、同時に下の攻撃スロットの結果が変わる。

### 攻撃 — 8 つのスロット

8 つの攻撃を、現在の守りの設定で実際に実行している。結果は枠の色と「通った / 防げた」だけで示し、文章は**選んだ 1 つ**にしか出さない。守りを外すと、そのとき通った攻撃が自動で選ばれ、**攻撃者が実際に手にした平文**が出る。

スロットの「この守りを外して試す」からも右のスイッチを操作できるので、守る側・攻める側どちらから入っても同じ因果に着く。

| 無効化する守り | 成立する攻撃 | なぜ防げるのか |
| --- | --- | --- |
| **証明書チェーン検証** | 中間者攻撃（偽 CA の証明書） | 信頼ストアのルート CA まで署名を辿れることを要求し、自称 CA を弾く。 |
| **ホスト名照合 (SAN)** | 別ドメインの正規証明書による成りすまし | 証明書の SAN に接続先が含まれることを要求し、他人の正規証明書を弾く。 |
| **有効期限・失効確認** | 期限切れ証明書の受理 | notBefore / notAfter の範囲内であることを要求する。 |
| **有効期限・失効確認** | 失効済み証明書の受理 | CRL / OCSP を引き、取り消された証明書を弾く。 |
| **CertificateVerify** | 証明書コピペ（秘密鍵なし） | ハンドシェイク全文への署名を要求し、鍵を持たない相手を弾く。 |
| **Finished / transcript hash** | ダウングレード攻撃 | 全メッセージのハッシュを鍵と MAC に縛り、書き換えを成立させない。 |
| **前方秘匿性 (ECDHE)** | 長期鍵の漏洩による遡及復号 | 鍵交換に使い捨て鍵を使い、接続終了時に捨てる。 |
| **レコード層の暗号化** | 盗聴（Cookie / トークンの窃取） | AEAD で暗号化し、同時に改ざん検知の認証タグを付ける。 |

いずれの攻撃も、対応する守り **1 つだけ**で結果が決まるように構成している。
そのために、攻撃ごとに「対象の守りはスイッチの値、それ以外はすべて ON」という設定で実行している（`attacks.ts` の `isolate`）。他を切っても結果は変わらないので、因果関係が 1 対 1 で読める。

### 見た目について

明るい盤面に振ってある。黒とグレーは使わず濃紺と青みのある紙を基準にし、青は「操作できるもの・進んだところ」だけに使う。意味を持つ色は 3 つに絞った（封がされている / 平文で流れている / 攻撃が通った）。5 つの層を 5 色に塗り分けることはしていない。絵文字は環境ごとに形が変わるので、必要な絵記号は `components/icons.tsx` に自分で描いてある。外部フォント・外部アセットの読み込みは無い。

## 本物との違い

**忠実に実装した部分**（RFC 8446 / 5869 の定義どおり）:

- HKDF-Extract / Expand、HKDF-Expand-Label、Derive-Secret のラベル構造
- 鍵スケジュールの段構成（Early → Handshake → Master、各段の `"derived"` 経由）
- traffic 鍵と IV の導出、`finished_key` と verify_data の計算
- CertificateVerify の署名対象（`0x20`×64 || コンテキスト文字列 || `0x00` || transcript hash）
- レコードごとの nonce（write_iv XOR 連番）と、レコードヘッダを追加認証データにすること
- ECDHE P-256、ECDSA P-256、AES-128-GCM（すべて Web Crypto の実物）

HKDF は RFC 5869 のテストベクタで、Early Secret は TLS 1.3 の既知の定数（`33ad0a1c…`）で検証している。

**簡略化した部分**:

- ハンドシェイクメッセージは TLS のバイナリ構造ではなく JSON。transcript hash はその決定的直列化に対して計算する
- 証明書は X.509 DER ではなく JSON。署名対象・検証手順の考え方は同じ
- HelloRetryRequest、セッション再開（PSK / 0-RTT）、鍵更新、クライアント証明書認証は未実装
- 暗号スイートは `TLS_AES_128_GCM_SHA256` のみ実装（ダウングレード攻撃で「選ばれる」弱いスイートは名前だけ）
- 「Finished 照合」を OFF にした状態は、**ハンドシェイク全文を鍵と MAC に縛らない古い設計**の模擬。TLS 1.3 にそういう設定は存在しない

## セキュリティ上の注意

このモックサーバーは**教材専用**であり、本番の TLS 実装として使ってはならない。
実装は攻撃の成立条件を分かりやすく見せることを優先しており、実運用に必要な処理（証明書パス構築の完全性、鍵の安全な破棄、タイミング攻撃対策、エラー処理の一様化など）は最小限にとどめている。
